# SonicStream Web PWA — Technical Documentation

This document describes the architecture, data model, and internals of the
**SonicStream Web PWA** (`web-pwa/`) — the cloud music player that streams the
audio produced by the SonicStream Windows desktop app.

> Companion docs: [PWA_FUNCTIONAL.md](PWA_FUNCTIONAL.md) (what it does / how to
> use it) and [DEPLOYMENT.md](DEPLOYMENT.md) (build + Azure deploy).

---

## 1. System overview

```
┌──────────────────────┐   download    ┌──────────────────────────┐
│  Desktop app         │──────────────▶│  Local disk               │
│  (main.py, yt-dlp)   │   audio mp3s  │  D:\...\YoutubeDownloads  │
└──────────────────────┘               └───────────┬──────────────┘
                                                    │ sync_azure_batch.py
                                                    │ (uploads basename == blob name)
                                                    ▼
                                        ┌──────────────────────────┐
                                        │  Azure Blob Storage       │
                                        │  stsonicstream / media    │
                                        │  - audio *.mp3 (blobs)    │
                                        │  - playlists_manifest.json│
                                        └───────────┬──────────────┘
                                                    │ SAS token (read-only)
                                                    ▼
┌───────────────────────────────────────────────────────────────────┐
│  Web PWA  (Azure Static Web App / any static host)                 │
│                                                                     │
│   index.html ──router──▶ desktop.html   (wide screens)             │
│                        └▶ mobile.html    (phones / home-screen app) │
│                                                                     │
│   Both shells load the SAME engine: app.js                          │
│                                                                     │
│   app.js:  manifest sync → IndexedDB → stream from blob → cache     │
└───────────────────────────────────────────────────────────────────┘
```

**Producer / transport / consumer:**

- **Producer** — the desktop app downloads audio locally.
- **Transport** — `sync_azure_batch.py` uploads the mp3s **and**
  `playlists_manifest.json` to the Azure Blob container. **The blob name is the
  on-disk file basename.**
- **Consumer** — the PWA reads the manifest, streams audio from the blob using a
  read-only SAS token, and caches blobs in IndexedDB for offline playback.

## 3. Configuration resolution

`app.js` resolves each config value (Azure account, container, SAS token,
client id, OneDrive link) with this precedence:

1. IndexedDB `settings` store (values the user saved in the Settings modal)
2. `localStorage` (`sonicstream_*` keys)
3. `window.SONICSTREAM_CONFIG` (from `config.js`)
4. `./settings.json` (fetched on launch; merged as defaults)
5. Hard-coded fallbacks (e.g. account `stsonicstream`, container `media`)

Azure blob base URL = `https://{account}.blob.core.windows.net/{container}`.
A media URL is `{blobBase}/{encodeURIComponent(file)}?{sasToken}`.

## 4. IndexedDB data model

**Database:** `SonicStreamPWA_DB`, version **5**. Three object stores:

| Store | keyPath | Contents |
|---|---|---|
| `settings` | `key` | `{ key, value, updated_at }` — Azure client id, SAS token, OneDrive link |
| `playlists` | `id` | Playlist objects with a `tracks[]` array. Stores the track **filename** (`file`), never the binary and never a domain/blob URL |
| `files` | `file_id` | The binary cache. `file_id` = the **filename** (e.g. `Song.mp3`). `{ file_id, blob, audio_blob, thumb_blob, title, normKey, id, meta, timestamp }` |

### Core design invariant

- The join between a **playlist track** and its **cached binary** is **by
  filename** (`track.file` === `files.file_id`), never by URL.
- **No domain / blob URL is ever persisted.** Playback and prefetch rebuild the
  Azure URL at runtime from the current config.
- **Why:** the cache stays valid across domain changes and SAS-token rotation —
  a cached file always resolves by name. The trade-off is that the manifest
  `file` value **must** equal the real Azure blob name (see §6).

Limits: per-file cap **20 MB** (`MAX_FILE_SIZE_BYTES`; larger files are skipped
for caching but still **stream** fine — the cap never blocks playback). Total
soft cap **10 GB** (`MAX_INDEXEDB_BYTES`). Oversized cached files are auto-purged
on startup (`purgeLargeFilesFromDB`).

## 5. Playlist sync flow

`syncDesktopPlaylists()` (triggered by desktop **Sync** / mobile **🔄 Refresh**,
and on startup via `loadPlaylistsFromDB()`):

1. Fetch the manifest in priority order:
   `./playlists_manifest.json` → `{blobBase}/playlists_manifest.json?{SAS}` →
   `/api/playlists/list` (local desktop server) → bundled
   `window.SONICSTREAM_MANIFEST_FALLBACK`.
2. Normalize each playlist/track into the engine shape.
3. `savePlaylistToDB()` each playlist into the `playlists` store; write per-track
   metadata rows into `files` (no blob yet).
4. Re-render the sidebar (desktop) and playlist cards (mobile).

## 6. Manifest generation (`deploy_pwa.py`) & the filename contract

`generate_pwa_manifest()` reads `history.json` and emits
`playlists_manifest.json` + `manifest_fallback.js`.

**Filename resolution (critical).** yt-dlp sanitizes titles when writing files —
most notably replacing `|` with the **fullwidth pipe `｜` (U+FF5C)** and other
OS-illegal characters. `sync_azure_batch.py` uploads each file under its on-disk
**basename**, so the blob name carries those sanitized characters. The manifest
`file` field must match the blob name exactly, or the SAS URL 404s.

`deploy_pwa.py` therefore resolves the **real on-disk filename** for each track:

- Prefer an explicit `file` already recorded on the history item.
- Else fuzzy-match the track title against a per-folder index built from the
  download directory (`_build_file_index` / `_clean_fuzzy`, the same rule
  `main.py` uses in `check_local_duplicate` / `build_sync_manifest`).
- Else fall back to `{title}.mp3`.

This mirrors the desktop's on-disk names, which are exactly the uploaded blob
names. (Regression fixed: previously the manifest used naive `{title}.mp3` with
an ASCII `|`, so ~204 tracks in "All Songs" alone 404'd.)

**Thumbnails.** Each track gets a real `thumbnail`
(`https://i.ytimg.com/vi/{id}/hqdefault.jpg` for 11-char YouTube ids, else the
gita cover). Each playlist's cover is set to its first song's thumbnail, so
playlists no longer collapse to one shared image. `app.js` also has
`getPlaylistThumbnail()` as a client-side fallback used by both shells.

## 7. Playback engine (`playTrack`)

Media URL resolution order for a track:

1. **Cached blob** in IndexedDB (`getTrackRecordFromDB` by filename) →
   `URL.createObjectURL(blob)` (100% offline).
2. `track.downloadUrl` (OneDrive Graph direct URL, if signed in).
3. **Azure blob** (on HTTPS): `{blobBase}/{encodeURIComponent(file)}?{SAS}`.
4. Local desktop server `/api/media/file/...` (when running on `127.0.0.1`).
5. YouTube stream via the local desktop server (last resort).

A Web Audio graph (`initWebAudioEngine`) adds a gain boost + compressor for
loud, in-car playback. `mediaSession` handlers expose play/pause/next/prev/seek
to lockscreen and car Bluetooth (AVRCP) controls.

Smart prefetch (`prefetchUpcomingTracks`) downloads the next N tracks' blobs into
IndexedDB in the background so playback is gap-free while driving.

## 8. Shared-engine DOM contract (mobile parity)

Both shells load the same `app.js`, which references many element ids. The rule:

- **`app.js` never assumes an element exists.** Every
  `getElementById(...).addEventListener(...)` is guarded (`if (el) ...`) so a
  shell that omits a control degrades gracefully instead of throwing. (A single
  unguarded reference to a missing element previously threw a `TypeError` that
  aborted `DOMContentLoaded` before bootstrap, leaving mobile with only a
  static player bar.)
- **Shared control ids** that must match for a feature to work on a shell:
  `audioElement`, `playerPlayPauseBtn` + `playIconSvg`, `playerPrevBtn`,
  `playerNextBtn`, `playerProgressBar`, `playerTrackTitle`/`Artist`/`Thumb`.
  `mobile.html` provides these in its docked player bar.
- Mobile-only ids: `mobilePlaylistsView`, `mobilePlaylistsList`,
  `mobileTracksView`, `mobileTrackList`, `mobileCurrentPlaylistTitle`,
  `btnSyncMobile`, `btnHardRefresh`.
- Mobile is **audio-only**: it ships no `<video>` element, and the video branch
  in `playTrack` is guarded (`isVideoTrack && videoElement`).

## 9. Service worker & updates

`sw.js` (cache `sonicstream-v2`) precaches the shell and uses stale-while-
revalidate for documents/scripts/styles. Because a pinned/home-screen app can
serve stale HTML/JS, the mobile header has an **Update** button (`btnHardRefresh`)
that:

1. Unregisters all service workers.
2. Deletes all Cache Storage entries.
3. Reloads with a `?v={timestamp}` cache-busting query.

Bumping `CACHE_NAME` also forces the `activate` handler to purge old caches.

## 10. IndexedDB Browser tool (`IndexDBbrowser.html`)

Standalone inspector: lists object stores with counts, paginates records, shows
blob sizes, maps `files` records back to referencing playlists ("Mapped
Playlists" column, built from the `playlists` store or the manifest), and
supports per-record / per-store deletion. Runs entirely client-side against
`SonicStreamPWA_DB`.

## 11. Known follow-ups

- The `files` store accumulates metadata-only rows (no blob) from manifest sync;
  harmless (playback checks `record.blob`) but can look like "cached" in the
  inspector.
- Tracks not present in the blob container (never downloaded/uploaded) fall back
  to `{title}.mp3` and will still 404 until they are downloaded + synced.
- Azure Blob **CORS**: cross-origin streaming through the Web Audio graph needs
  the storage account to allow the site origin. If gain-boosted playback fails
  cross-origin, add a CORS rule (see DEPLOYMENT.md).
